\section{Mini-Internet con fragmentación}
Esta actividad extiende el mini-Internet de forwarding básico con fragmentación IP. Cada router escucha paquetes simulados mediante UDP, consulta su tabla de rutas y obtiene tanto el siguiente salto como el MTU del enlace. Si el paquete supera ese MTU, lo divide antes de reenviarlo; un fragmento puede volver a fragmentarse en un enlace posterior. Cuando el destino es el router local, los fragmentos se almacenan por ID y se intenta reensamblar el datagrama cada vez que llega uno.

\subsection{Objetivo y continuidad con la actividad anterior}
La implementación conserva el forwarding, el TTL y el round-robin de la actividad anterior. El cambio principal es que el paquete ya no contiene solo IP, puerto, TTL y mensaje: ahora incluye los campos necesarios para identificar y reconstruir un datagrama fragmentado. La actividad se valida primero con pruebas unitarias y luego con la red de cinco routers y sus MTU.

\subsection{Tabla de rutas y MTU}
Las tablas mantienen la red de destino, el rango de puertos y el siguiente salto, pero agregan al final el MTU del enlace. Por ejemplo, la ruta de R1 hacia R5 es:
\begin{salida}
127.0.0.1/24 8882 8885 127.0.0.1 8882 100
\end{salida}
La función \code{check\_routes} retorna \code{((IP, puerto), MTU)}. Las rutas alternativas de un área siguen usando round-robin y cada área conserva su propia posición, de modo que añadir el MTU no cambia la decisión de ruta.

\subsection{Router y forwarding}
El router se ejecuta con \code{python3 router.py router\_IP router\_puerto router\_rutas.txt}. Lee las tablas con el MTU, descarta paquetes con TTL 0 y, antes de reenviar, disminuye el TTL y llama a \code{fragment\_IP\_packet}. Cada fragmento se envía al mismo siguiente salto. Como el MTU se consulta en cada router, un fragmento recibido puede volver a fragmentarse para el enlace siguiente.

\subsection{Estructura del paquete IP}
Se eligió un header de 18 bytes. La IP ocupa cuatro bytes, el puerto dos, el TTL uno, el ID dos, el offset cuatro, el tamaño del mensaje cuatro y FLAG uno. El offset se expresa en bytes, tal como pide la actividad; el tamaño no incluye el header y FLAG vale 1 si quedan fragmentos o 0 en el último.

\begin{table}[ht]
\centering
\caption{Estructura del paquete IP de la actividad 6.}
\label{tab:header-fragmentacion}
\begin{tabular}{lll}
\hline
Bytes & Campo & Codificación \\
\hline
{[0:4]} & IP de destino & un byte por número de a.b.c.d \\
{[4:6]} & Puerto de destino & entero sin signo, big-endian \\
{[6]} & TTL & entero sin signo de 1 byte \\
{[7:9]} & ID & entero sin signo de 2 bytes, big-endian \\
{[9:13]} & Offset & entero sin signo de 4 bytes, en bytes \\
{[13:17]} & Tamaño & tamaño de message, sin header \\
{[17]} & FLAG & 1 si quedan fragmentos, 0 si es el último \\
{[18:]} & Mensaje & bytes \\
\hline
\end{tabular}
\end{table}

\subsection{Decisiones de diseño}
\begin{itemize}
\item Se usan dos bytes para el ID, permitiendo valores de 0 a 65535, y cuatro bytes para el offset y el tamaño, manteniendo el header compacto y suficiente para los casos de la actividad.
\item \code{parse\_packet} valida que el paquete tenga header completo, que FLAG sea 0 o 1 y que el tamaño declarado coincida con los bytes recibidos. \code{create\_packet} valida los rangos antes de construir el paquete.
\item \code{fragment\_IP\_packet} retorna \code{[IP\_packet]} si el paquete completo cabe en el MTU. En otro caso usa \code{MTU - 18} bytes de mensaje por fragmento y conserva el offset inicial.
\item Al refragmentar, FLAG se conserva en el último subfragmento del fragmento original; los subfragmentos anteriores reciben FLAG 1. Así, el último fragmento original sigue señalando el final del datagrama completo.
\item \code{reassemble\_IP\_packet} ordena por offset, comprueba identidad, continuidad y FLAG, y retorna None mientras falte información. El diccionario \code{received\_packets} usa el ID como llave y conserva la lista de bytes recibidos.
\end{itemize}

\subsection{Fragmentación y reensamblaje}
\code{fragment\_IP\_packet} primero compara el tamaño total, incluyendo header, con el MTU. Al fragmentar, cada paquete tiene su propio header, su offset y su tamaño. En destino, el router agrega cada fragmento a la lista asociada a su ID e intenta reensamblar inmediatamente. El orden de llegada no importa: la función ordena por offset y solo imprime el campo \field{message} cuando recibe un datagrama completo.

\section{Pruebas de la actividad 6}
Las pruebas se realizaron sobre las funciones sin levantar sockets y sobre la configuración de cinco routers con MTU. La suite principal es \code{python3 pruebas/test\_funciones.py}; termina con ``Todas las pruebas pasaron''.

\subsection{Parsing, TTL y rutas}
Se verificó que \code{parse\_packet} y \code{create\_packet} sean inversas con el nuevo header, incluyendo ID, offset, tamaño y FLAG, además de paquetes truncados, tamaños inconsistentes, TTL, puerto y FLAG fuera de rango. También se comprobó que \code{check\_routes} retorne el siguiente salto junto con su MTU. El paquete pequeño del enunciado usa IP 127.0.0.1, puerto 8885, TTL 10, ID 347, offset 0, tamaño 5, FLAG 0 y mensaje ``hola!''; al reenviarse desde R1 conserva el ID y pasa a TTL 9.
\begin{salida}
parse_packet(IP_packet_v1) =
{'ip': '127.0.0.1', 'port': 8885, 'ttl': 10, 'id': 42,
 'offset': 3, 'size': 4, 'flag': 1, 'message': b'hola'}
IP_packet_v1 == IP_packet_v2 ? True
parse_packet(b'') -> ValueError
parse_packet con tamaño declarado incorrecto -> ValueError
create_packet con TTL 256 -> ValueError
create_packet con puerto 70000 -> ValueError
create_packet con FLAG 2 -> ValueError
\end{salida}
Para las tablas con MTU, las consultas de rutas produjeron:
\begin{salida}
R1 hacia R5 -> (('127.0.0.1', 8882), 100)
R2 hacia R5 -> (('127.0.0.1', 8883), 50)
R2 hacia R5 -> (('127.0.0.1', 8884), 80)
\end{salida}
Para el paquete pequeño, el test de forwarding produjo:
\begin{salida}
paquete de 5 bytes no se fragmenta -> 1
TTL del paquete reenviado -> 9
ID del paquete reenviado -> 347
destino del primer salto -> ('127.0.0.1', 8882)
\end{salida}

\subsection{Fragmentación y refragmentación}
Para un paquete de 100 bytes de mensaje y MTU 50 se obtuvieron cuatro fragmentos de tamaños totales 50, 50, 50 y 22, con offsets 0, 32, 64 y 96 y FLAG 1, 1, 1 y 0. También se comprobó que un paquete que cabe en el MTU retorna una lista de un elemento.
\begin{salida}
cantidad de fragmentos para MTU 50 -> 4
tamaño total de cada fragmento -> [50, 50, 50, 22]
offsets -> [0, 32, 64, 96]
FLAG -> [1, 1, 1, 0]
reensamblaje del paquete completo con fragmentos desordenados -> correcto
lista incompleta de fragmentos -> None
\end{salida}

La prueba de refragmentación usa un paquete total de 150 bytes. R1 lo divide con MTU 100 en fragmentos de 100 y 68 bytes. Luego R2 los recibe y aplica round-robin entre sus dos rutas: el primer fragmento se envía hacia R3 con MTU 50, por lo que sus 82 bytes de mensaje se dividen en tres subfragmentos; el segundo se envía hacia R4 con MTU 80, por lo que sus 50 bytes de mensaje caben en un solo fragmento. Por eso R2 reenvía cuatro fragmentos en total (tres más uno). Todos caben en el MTU de su enlace y conservan el ID y los offsets necesarios.
\begin{salida}
paquete de 150 bytes fragmentado en R1 -> 2
tamaño de fragmentos enviados por R1 -> [100, 68]
refragmentación realizada por R2 -> True
R2 reenvía 4 fragmentos -> 4
\end{salida}

\subsection{Llegada desordenada e IDs intercalados}
Se construyeron dos datagramas con IDs 101 y 202, se fragmentaron y se entregaron en orden desordenado e intercalado. El router mantuvo dos listas independientes en \code{received\_packets}, no reenvió esos paquetes y solo imprimió cada mensaje cuando la lista correspondiente pudo reensamblarse. Este test verifica que los fragmentos de un ID no se mezclen con los de otro.
\begin{salida}
IDs almacenados -> {101, 202}
mensajes reensamblados en orden de llegada completa ->
['ABCDEFGHIJKLMNO', '1234567890abcde']
fragmentos locales no reenviados -> []
\end{salida}

\subsection{TTL y round-robin con MTU}
Las pruebas conservan la regresión del TTL: los paquetes con TTL 0 se descartan, los reenviados disminuyen su TTL en uno y los destinados al router local se procesan solo si tienen TTL positivo. En R2, las consultas hacia R5 alternan los siguientes saltos y sus MTU:
\begin{salida}
127.0.0.1:8883, MTU 50
127.0.0.1:8884, MTU 80
127.0.0.1:8883, MTU 50
127.0.0.1:8884, MTU 80
\end{salida}

\subsection{Prueba de integración manual}
Para probar la red completa se levantan las cinco tablas con MTU:
\begin{salida}
python3 red.py rutas/rutas_R1_v3_mtu.txt rutas/rutas_R2_v3_mtu.txt rutas/rutas_R3_v3_mtu.txt rutas/rutas_R4_v3_mtu.txt rutas/rutas_R5_v3_mtu.txt
\end{salida}
En otra terminal se ejecutaron dos casos, reiniciando la red entre ellos para mantener cada datagrama aislado. Esto es necesario porque \code{enviar.py} construye el paquete con el ID predeterminado 0; si se envían dos datagramas con ese mismo ID mientras el router conserva su diccionario, sus fragmentos se agrupan en una misma lista.

Primero se envió el paquete pequeño del enunciado:
\begin{salida}
python3 enviar.py 127.0.0.1 8885 "hola!" 127.0.0.1 8881 10
\end{salida}
La salida real mostró que llegó a R5 y que el TTL se redujo en cada salto:
\begin{salida}
[R1] ... TTL=9 ... hacia 127.0.0.1:8882
[R2] ... TTL=8 ... hacia 127.0.0.1:8883
[R3] ... TTL=7 ... hacia 127.0.0.1:8882
[R2] ... TTL=6 ... hacia 127.0.0.1:8884
[R4] ... TTL=5 ... hacia 127.0.0.1:8882
[R2] ... TTL=4 ... hacia 127.0.0.1:8883
[R3] ... TTL=3 ... hacia 127.0.0.1:8885
[R5] hola!
\end{salida}
El camino observado fue R1--R2--R3--R2--R4--R2--R3--R5, con siete reenvíos.

Luego se envió un paquete de 150 bytes totales, formado por un mensaje de 132 caracteres:
\begin{salida}
python enviar.py 127.0.0.1 8885 "X..." 127.0.0.1 8881 10
\end{salida}
R1 lo envió a R2 en dos fragmentos. En esa ejecución R2 eligió primero la ruta hacia R4, de MTU 80, y luego la ruta hacia R3, de MTU 50. Los routers intermedios volvieron a fragmentar esos paquetes según sus enlaces; finalmente R5 imprimió el mensaje completo. Las líneas siguientes son solo las principales: se omitieron mensajes intermedios de forwarding de fragmentos que regresaron a R2 para mantener la salida legible.
\begin{salida}
[R1] ... TTL=9 ... hacia 127.0.0.1:8882
[R2] ... TTL=8 ... hacia 127.0.0.1:8884
[R2] ... TTL=8 ... hacia 127.0.0.1:8883
[R4] ... TTL=7 ... hacia 127.0.0.1:8885
[R3] ... TTL=7 ... hacia 127.0.0.1:8885
[R5] X...
\end{salida}
La salida completa mostró además que algunos fragmentos recorrieron R4--R2 o R3--R2 antes de llegar a R5. Por tanto, la prueba real confirmó fragmentación en R1, refragmentación en routers posteriores, decremento del TTL y reensamblaje correcto en R5.

También se repitió el envío del mismo datagrama de 150 bytes iniciándolo desde R2, R3 y R4, siempre con destino R5 y TTL 10. En cada caso se reinició la red antes de enviar para evitar mezclar el ID predeterminado 0 con el caso anterior. Los tres mensajes llegaron completos a R5:
\begin{itemize}
\item Desde R2, la primera ruta elegida fue R2--R3. R3 refragmentó el datagrama hacia R2 y hacia R5; R2 y R4 participaron en reenvíos posteriores, y R5 imprimió el mensaje completo:
\begin{salida}
[R2] ... TTL=9 ... hacia 127.0.0.1:8883
[R3] ... TTL=8 ... hacia 127.0.0.1:8882
[R3] ... TTL=8 ... hacia 127.0.0.1:8885
[R2] ... TTL=7 ... hacia 127.0.0.1:8884
[R4] ... TTL=6 ... hacia 127.0.0.1:8885
[R5] X...
\end{salida}
\item Desde R3, el paquete pasó primero por R2. R2 lo dividió entre las rutas hacia R3 y R4; posteriormente algunos fragmentos regresaron a R2 antes de que R3 y R4 los entregaran a R5:
\begin{salida}
[R3] ... TTL=9 ... hacia 127.0.0.1:8882
[R2] ... TTL=8 ... hacia 127.0.0.1:8883
[R2] ... TTL=8 ... hacia 127.0.0.1:8884
[R3] ... TTL=7 ... hacia 127.0.0.1:8885
[R4] ... TTL=7 ... hacia 127.0.0.1:8885
[R5] X...
\end{salida}
\item Desde R4, el paquete pasó primero por R2. R2 lo dividió entre las rutas hacia R3 y R4; se observaron subfragmentos adicionales que circularon entre R2, R3 y R4, y finalmente R5 imprimió el mensaje completo:
\begin{salida}
[R4] ... TTL=9 ... hacia 127.0.0.1:8882
[R2] ... TTL=8 ... hacia 127.0.0.1:8883
[R2] ... TTL=8 ... hacia 127.0.0.1:8884
[R3] ... TTL=7 ... hacia 127.0.0.1:8885
[R4] ... TTL=7 ... hacia 127.0.0.1:8885
[R5] X...
\end{salida}
\end{itemize}
En estas salidas se representa el mensaje largo como \texttt{X...} para evitar desbordar el margen; en la ejecución real R5 imprimió los 132 caracteres completos. Las salidas son representativas: las líneas completas de forwarding se omitieron por extensión, especialmente los mensajes intermedios de fragmentos que regresaron a R2. Las pruebas muestran que el router de entrada puede cambiar el camino y el número de refragmentaciones, pero el datagrama se reensambla correctamente en R5 en los tres casos.
